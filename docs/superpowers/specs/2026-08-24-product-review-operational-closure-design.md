# Product Review Operational Closure Design

## Decision and scope

**Convergence mode:** `OPERATIONAL_CLOSURE`

JW Studio will close the customer product-review loop across the authenticated customer account, protected Admin moderation workflow, and public PDP. Laravel and MySQL own all business state. The latest Google AI Studio exports are the visual authority for the selected Admin and PDP review regions.

The approved decision is to retire the legacy manually editable PDP rating, review-count and sample-review workflow from all operational and Storefront consumers. Legacy database records remain intact for compatibility and are not deleted in this batch.

### Included

- Customer review submissions already rendered on Account > Purchase History, including private images and re-submission after rejection.
- Admin Catalog Hub review card, sidebar/route entry, moderation list, filters, batch actions, rejection reason flow, image viewer, detail drawer, audit history and product-editor read-only summary.
- Real Admin API bindings and permission-aware actions.
- PDP rating summary and Reviews accordion based exclusively on published, order-linked `ProductReview` records.
- Automated and authenticated browser evidence for the full submit -> approve -> public PDP path.

### Excluded

- Ratings/helpful-votes generated by customers, review replies, public review search, third-party review syndication, Marketplace reviews, notification emails, real external moderation services, and deletion/migration of legacy PDP-review tables.

## Architecture

```text
Delivered order item
  -> customer review submission service
  -> product_reviews + product_review_media + product_review_events
  -> protected Admin Review API and moderation service
  -> published status only
  -> Storefront PDP view model and source-faithful review UI
```

### Data and lifecycle rules

- `product_reviews` is the only operational review source. The order item, product, customer and submitted product/variant/order text are immutable submission snapshots.
- A delivered order item may have many historical rejected attempts but at most one `pending` or `published` attempt, enforced by `active_lock`.
- `pending -> published` makes the review and its approved media eligible for the PDP. `pending|published -> rejected` removes public eligibility and appends an audit event.
- A rejection frees `active_lock`; a new customer submission becomes a new `attempt_number`, never overwriting earlier history.
- `ProductReviewMedia` is private by default. Authorization gates protect customer ownership and Admin view permission. Published-public delivery is a separately checked behavior and must never expose pending/rejected media.
- Rating and count are system-managed, realtime aggregates of published reviews. They are not editable catalog fields.

### Admin integration

1. Add `catalog-reviews` to the Admin route union, route map, active Catalog group and `App.tsx` dispatcher.
2. Port the three approved ZIP review regions without altering their source DOM hierarchy or Tailwind classes. Only replace context data/events at the narrow adapter boundary.
3. Add `reviewData.ts`, following the existing `catalogData.ts` authenticated fetch pattern. It maps protected Laravel JSON to the ZIP view model and invokes list, audit, single-moderate and bulk-moderate endpoints.
4. Extend `window.__JW_ADMIN__` with Review API URLs and currently granted review permissions. The client uses these only to render allowed actions; Laravel remains the permission authority.
5. Use optimistic state only after a successful API response; re-fetch affected reviews/audit history after each mutation. No review data may use localStorage or ZIP mock data.
6. Replace the Product Editor's mutable social-proof controls and sample-review handlers with the ZIP's read-only computed summary and a product-filtered Moderation Hub deep link.

### Protected API view model

Existing endpoints remain protected and gain only fields required by the approved source UI:

- List row: product ID/title/handle/thumbnail, customer ID/name/email, order ID/number, variant snapshot, rating, title/comment, status, submitted/published/moderated timestamps, moderator name, rejection note and authorized media URLs.
- Detail drawer: the row model plus authorized audit events from `/api/reviews/{review}/audit`.
- Mutations: `publish` and `reject` through existing single/bulk endpoints. API returns normalized updated rows or per-item bulk results so the UI does not infer state.
- Customer email and private media URLs remain Admin-only; no field is added to Storefront responses.

### PDP integration

- The controller continues to eager-load `reviews` constrained to `published` and their eligible media.
- The PDP rating row and reviews accordion use the exact approved ZIP structure, conditional only on a non-zero published-review count.
- The aggregate is computed from the loaded published collection. Each item shows its real rating, title, comment, published date and system-validated `Verified Studio Buyer` marker.
- Zero published reviews hides both the rating row and review accordion. Pending, rejected, manual seed and legacy `ProductPdpReview` records are never included.

### Legacy source retirement

- `ratingScore`, `reviewCount`, `reviews` and `ProductPdpReview` remain stored only as dormant historical data.
- `CatalogApiController` no longer accepts or persists manual review/rating fields for the Product Editor review UI.
- Product Editor no longer offers sample-review loading, adding, deleting or manual star/count editing.
- Existing migration and records are retained; no destructive data operation is in scope.

## Error and permission behavior

- Unauthorized requests return existing 403 responses. Admin UI hides disallowed actions but shows no fabricated data or success state.
- Validation or transition errors retain the source dialog/drawer state and show the API's stable message through existing Admin toast/error patterns.
- Empty moderation tabs use the exact ZIP empty state. A zero-PDP-review product hides the complete review source region rather than showing invented ratings.
- A failed media request does not expose a fallback public path or private filename.

## Acceptance plan

1. PHPUnit: submission eligibility, one active attempt, rejection/retry, media type/size/privacy, role permissions, single/bulk transitions, audit events, legacy-field non-consumption, published-only PDP query/rendering.
2. Admin unit tests: adapter mapping, route selection, permission-gated actions and no mock/localStorage review owner.
3. Browser: authenticated customer submits a review with image; authorized Admin sees it; Admin publishes; fresh PDP in a separate session shows its rating/content; rejection makes it disappear; a new attempt is allowed; batch action writes a shared audit batch ID.
4. Fidelity: capture source and Laravel desktop/mobile screenshots for the selected Admin and PDP regions; compare all source-visible controls, spacing, empty states, drawer/modal and responsive structure.
5. Closure gate: mark `OPERATIONAL_CLOSURE` only after persistence across refresh/re-login, authorization checks and downstream PDP proof all pass.

## Risks and mitigations

- **Stale Admin mock state:** avoid importing `mockReviewsData.ts` or localStorage review handlers; adapter tests block it.
- **Legacy manual social proof returning through catalog save:** strip the old mutable UI controls and reject/ignore their review fields at the Admin contract boundary.
- **Private photo leak:** media access uses review policy plus status checks; all relevant browser/API paths are tested.
- **UI divergence:** copy only the approved component structures/classes and inject data/events; do not redesign adjacent catalog/PDP regions.
