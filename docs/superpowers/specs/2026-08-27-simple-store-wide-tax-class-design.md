# Simple Store-Wide Tax Class Design

**Status:** approved in conversation; awaiting written-spec review.

## Purpose

Replace the current zone-and-rule tax engine with one merchant-controlled, store-wide percentage charge. The merchant may maintain multiple Tax Classes such as `SST`, `GST`, or `Service Charge`, but no more than one may be active. Every sellable product automatically uses the active class; products no longer carry tax assignments.

The design deliberately removes jurisdiction matching and advanced tax-policy behavior. JW Studio applies only the percentage explicitly configured by the merchant and does not infer legal treatment.

## Scope

### Included

- Add, edit, activate, deactivate, and delete Tax Classes.
- Tax Class name, percentage, and active status.
- Zero or one active class, enforced transactionally and at the database boundary.
- Store-wide calculation on discounted merchandise.
- Server-authoritative Cart, Cart Drawer, Checkout, and order tax values.
- Immutable order tax snapshots.
- Source-faithful simplified Admin UI generated by Google AI Studio.
- Safe removal of current browser-acceptance tax records and product assignments.

### Excluded

- Product-specific tax classes.
- Countries, states, postcodes, Tax Zones, and jurisdiction matching.
- Separate Tax Rules.
- Shipping, payment-surcharge, or COD-fee taxation.
- Compound taxes and rule priorities.
- Effective dates and scheduled rates.
- Tax-inclusive catalog prices.
- Registration/compliance metadata and tax filing.
- Refund tax allocation, credit notes, and partial-refund tax recomputation.

## Tax Class Model

`tax_classes` is the only operational tax-configuration table.

| Field | Contract |
| --- | --- |
| `id` | Primary key |
| `name` | Required merchant label; unique case-insensitively |
| `rate_percent` | Decimal percentage from `0.0000` through `100.0000` |
| `is_active` | Merchant-visible active status |
| `active_slot` | Internal nullable singleton marker; value `1` only for the active row |
| timestamps | Created and updated audit timestamps |

A unique index on `active_slot` makes two active rows impossible. Inactive rows use null, allowing any number of inactive classes. All activation writes run in a transaction with row locks: clear the previous active row, then enable the selected row.

The system permits zero active classes. This is the safe unconfigured state.

## Calculation Contract

The only calculation is:

```text
taxable merchandise = max(0, subtotal - merchandise discount)
tax = round_half_up(taxable merchandise * active rate / 100)
grand total = taxable merchandise + shipping + payment surcharge + tax
```

All money is represented as integer cents. Rate precision is stored to four decimal places. A single integer-safe rounding implementation is used by Cart and Checkout.

Shipping, payment surcharge, and COD fees are never part of the taxable base. A missing active class returns zero tax with an unconfigured status. An active 0% class returns zero tax with a matched-zero-rate status and retains the class identity.

`TaxQuoteService` remains the single server authority but is simplified to resolve the active Tax Class rather than product classes, zones, or rules. Browser JavaScript only renders the returned summary.

## Admin UI

The canonical page becomes `/admin/settings/tax-classes`. `/admin/settings/tax-zones` redirects to the new route during compatibility. Settings navigation uses `Tax Classes`.

The approved Google AI Studio source must provide one page containing:

- Page title and short store-wide explanation.
- `Add Tax Class` action.
- Table columns: Name, Rate, Status, Actions.
- Add/Edit modal fields: Tax Class Name, Tax Rate (%), Active.
- Actions: Edit, Activate or Deactivate, and Delete.
- Existing project toast, validation, confirmation, loading, dark/light, and responsive patterns.
- Empty/unconfigured warning: `No active Tax Class. New orders will not be charged tax.`

Activating a class prompts for confirmation and automatically deactivates the current class. The active class cannot be deleted. An inactive class may be deleted. Duplicate names and percentages outside 0–100 produce inline/stable validation errors.

The following UI is removed from the operational page:

- Tax Rates tab and rule matrix.
- Geo Tax Zones tab.
- Tax Engine Configuration tab.
- Live Tax Rate Inspector.
- Product Editor Tax Class field.

## Admin API

The operational API is:

- `GET /admin/api/tax-classes`
- `POST /admin/api/tax-classes`
- `PATCH /admin/api/tax-classes/{taxClass}`
- `POST /admin/api/tax-classes/{taxClass}/activate`
- `POST /admin/api/tax-classes/{taxClass}/deactivate`
- `DELETE /admin/api/tax-classes/{taxClass}`

Only authenticated Admin users may call these endpoints. Responses return the canonical list plus active identity where useful so the React state can rehydrate from MySQL after every mutation.

The existing complex `/admin/api/tax-settings/*` routes leave UI use. During a compatibility period, mutating legacy routes return an explicit deprecated response rather than silently maintaining a second configuration system.

## Storefront Behavior

PLP and PDP remain tax-exclusive and require no tax-price redesign.

Cart, Cart Drawer, and Checkout render the server summary:

- Active positive rate: `SST (8%)` and the calculated amount.
- Active zero rate: the configured name and `0%`, with RM0.00.
- No active class: omit the entire tax row.

The label is the merchant-entered Tax Class name. JW Studio does not reinterpret labels such as SST, GST, or Service Charge.

Address and shipping-quote changes do not alter the tax rate or taxable base except when a merchandise discount changes. Checkout authorization always recalculates with the active class at that instant. A rate switch while Checkout is open therefore changes the authorized total to the latest active configuration.

## Immutable Order Evidence

At authorization, the order stores one immutable tax snapshot when an active class exists, including an active 0% class:

- Nullable Tax Class ID.
- Tax Class name.
- Rate percentage.
- Taxable merchandise amount.
- Tax amount.
- Calculation mode `store_wide_percentage`.
- Quoted timestamp.

Order Detail, Order Success, and receipts read the snapshot, never the current Tax Class. Renaming, changing, deactivating, or later deleting a class cannot rewrite historical orders.

## Refund Boundary

The existing refund flow continues to accept a total refund amount and reason. It does not allocate the refund among merchandise, shipping, tax, or goodwill, and it does not modify the original order tax snapshot. Tax credit notes and refund-tax adjustment lines are outside this design.

## Migration

The cutover performs these bounded changes:

1. Add `rate_percent` and the database-backed singleton-active marker to `tax_classes`.
2. Remove the known Browser Acceptance and Closure Proof class/zone/rule records created for local testing.
3. Clear every `products.tax_class_id` value.
4. Remove product tax-class fields from Admin API payloads, TypeScript contracts, and Product Editor UI.
5. Stop all runtime reads from `tax_zones`, `tax_rules`, and complex `tax_configurations`.
6. Keep legacy tables dormant for rollback during the first release; do not expose them in Admin or Checkout.
7. Begin with no active Tax Class and therefore zero tax on new carts/orders.
8. Preserve existing `order_tax_lines` and configuration snapshots unchanged.

Physical removal of legacy tables and the deprecated product column is a later cleanup migration after operational acceptance, not part of this cutover.

## Failure Handling and Concurrency

- Duplicate names, invalid rates, attempts to delete the active row, and malformed requests return stable 422 responses.
- Activation locks Tax Class rows and relies on the unique active marker to prevent concurrent dual activation.
- Checkout reads and snapshots the active class inside its existing order transaction.
- A class may be edited or deleted only through the canonical service/API path.
- Missing configuration never falls back to a static percentage.
- Cart or Checkout must not trust a browser-provided name, rate, or tax amount.

## Testing and Acceptance

Automated tests prove:

- No active class produces zero tax and the storefront omits the row.
- Active 0% preserves its identity and produces zero tax.
- Tax uses discounted merchandise only.
- Shipping and payment surcharges remain untaxed.
- Only one class can be active, including concurrent activation attempts.
- Activating one class deactivates the previous class.
- Active deletion fails; inactive deletion succeeds.
- CRUD and activation require Admin authentication.
- Cart, Checkout, order aggregate, and immutable snapshot agree.
- Historical snapshots survive class rename, rate change, deactivation, and deletion.
- Legacy zone/rule/product-assignment data no longer affects quotes.

Authenticated browser acceptance on the actual XAMPP runtime proves:

1. Create and activate `SST 8%`.
2. Verify the discounted-merchandise Checkout calculation.
3. Place a local test order and inspect its immutable snapshot.
4. Create and activate `GST 6%`; verify SST becomes inactive.
5. Verify a new Checkout uses GST while the old order still shows SST.
6. Deactivate GST and verify the storefront hides the tax row.
7. Delete an inactive class.
8. Verify MySQL persistence after refresh/re-login.
9. Check browser console and network failures.
10. Capture before/after screenshots and update the closure mapping.
